# ADR-003: 코디네이터 무인 진행·사용량 가드(선택)·세션 인계

- 날짜: 2026-10-02
- 상태: 적용
- 범위: Orca 코디네이터의 승인 대기, 사용량 관리, 세션 수명
- 보완: [ADR-002](ADR-002-orca-orchestration.md)의 결정 4(모델 배정 사용자 승인)와 「결과와 제한」(배정안 승인 전에는 워커가 뜨지 않음, 사용량 미계산, 코디네이터 상주). 모델 선택 표는 바꾸지 않는다.

## 배경

ADR-002 이후 하네스는 세 가지를 사람이 곁에 있다고 가정했다.

1. **승인 대기**: 배정안과 재승인 대상 변경(Story 분할 포함)마다 사용자의 OK를 기다린다. 답이 없으면 승인으로 보지 않는다.
2. **사용량 미계산**: Orca가 사용량을 명령으로 주지 않아 계산하지 않고, 한도 오류가 나면 대체 모델로 넘긴다.
3. **코디네이터 상주**: 코디네이터가 Epic 내내 한 세션으로 돈다. 바꿀 때는 사람이 「이어서 하기」를 친다.

같은 조직의 다른 저장소에서 같은 Orca·Claude Code·Codex 구성으로 여러 Epic을 무인으로 돌린 운영 기록에서 셋이 각각 문제가 됐다.

- 긴 Epic은 스펙 단계에서 Story를 여러 번 나눈다(한 Epic에서 수십 번). 분할마다 승인을 기다리면 밤사이 진행이 첫 분할에서 멈춘다.
- 주간 한도를 며칠에 나눠 쓰는 운영(하루 몫을 정하고 매일 올림)은 사용률을 읽을 수 있어야 한다. 한도 오류를 기다리는 방식으로는 바닥나기 전에 멈출 수 없다. 사용률은 읽을 수 있었다: Claude Code는 Pro/Max 구독이면 statusline 입력에 주간 사용률을 주고, Codex는 대화 기록(rollout)의 `token_count` 이벤트에 `rate_limits`를 남긴다.
- 코디네이터 한 세션이 길어지면 매 턴 옛 맥락을 다시 읽어 비용이 커졌다(한 세션이 한 묶음의 마감에 209턴·약 630만 토큰). 그 뒤로 묶음마다 새 세션으로 넘겨 여러 Epic을 사람 손 없이 이었다. 인계 전후 비용을 같은 조건으로 비교한 기록은 없다.

## 결정

1. **진행 방식을 둘로 둔다.** 기본은 지금처럼 승인 대기다. 시작 프롬프트에서 **무인**을 고르면 코디네이터는 질문으로 턴을 끝내지 않고, 배정안을 규칙대로 적용하며, Story 분할은 부모 행을 물려받아 진행한다. 사람 대신 정한 것은 `reviews/epic-<N>/owner-digest.md`에 「결정 — 적용 — 근거 — 뒤집으면」으로 남기고, 멈출 때의 보고를 미확인 항목 수로 시작한다. 위험을 줄이는 장치(다른 회사 리뷰, 검증, 수락 기준, push·merge·배포 승인 범위)는 무인에서도 그대로다 — 바꾸는 것은 **기다림**뿐이다. 그 밖의 재승인 대상(리뷰 약화, effort 하향, 배정안 밖 모델, 범위 확장)은 무인에서 하지 않고 그 Story를 보류한다. (orca-rules §4.2)
2. **사용량 가드를 선택 기능으로 둔다.** 기본은 꺼져 있다(ADR-002와 같다). 사용자가 `~/.orchestrator/limits.json`을 만들면 켜지고, 키마다 따로 켠다. 한도는 계정 단위라 사용자 폴더에 둔다. Claude는 statusline 기록 장치(`install-statusline-tee.mjs`)로, Codex는 작은 탐침 호출로 읽는다. Claude 한도에 닿으면 새 워커를 띄우지 않고 지금 Story까지 통합한 뒤 멈춘다. Codex는 경계 둘(light: Sol 구현을 승인된 대체 모델로, exhausted: Codex를 부르지 않고 Sol 리뷰가 필요한 Story는 보류)로 나눈다. 대체 모델 전환은 이미 사전 승인 대상이라 새 승인 규칙이 생기지 않는다. 멈춤 파일(`STOP`, `STOP-<저장소>`)은 한도와 무관하게 언제든 멈춘다. (orca-rules §8.1)
3. **코디네이터를 Story 몇 개마다 새 세션으로 인계한다.** 안전한 경계(실행 중 워커 없음, 통합·기록 커밋 뒤)에서 인계문(`state/orca/handoff/`)을 쓰고 `scripts/orca/session-rollover.mjs`가 같은 모델의 새 Claude Code 탭을 Orca로 띄워 한 줄로 넘긴다. 후임은 `orca orchestration run-use`로 같은 Run에 붙고 앞 탭을 닫는다. 준비 판정은 화면으로 하고(`tui-idle`은 Claude가 뜨기 전에도 만족된다), 후임 모델을 배너로 대조하며, 전송은 Orca 영수증과 같은 요청 ID 재전송으로 확정한다 — 불확실하면 다시 보내지 않는다(코디네이터 둘이 더 나쁘다). 체인 상한으로 폭주를 막는다. (orca-rules §11)

## 고려한 대안

1. **승인 대기를 없애고 항상 무인**
   - 장점: 규칙이 한 벌이다.
   - 단점: 사람이 곁에 있을 때 배정을 고르는 이점을 잃는다. 처음 쓰는 프로젝트는 승인 대기로 시험 운영하는 편이 낫다.
2. **Orca decision gate(`gate-create`)로 사람 결정을 막아 두기**
   - 장점: Orca가 막힌 Task를 추적한다.
   - 단점: 결정이 필요한 Story만이 아니라 의존 구조 전체를 Orca Task로 모델링해야 하고, 이 하네스의 상태 파일(`sprint-status.yaml`·계획 파일)과 이중 기록이 된다. 하네스 문서(owner-digest·계획의 「결정 대기」)로 충분했다.
3. **사용량을 프로젝트 `state/orca/`에 기록**
   - 장점: 저장소 하나 안에서 끝난다.
   - 단점: 한도는 계정 단위라 같은 계정의 여러 저장소가 각자 다른 한도를 보게 된다.
4. **인계를 Orca 내장 기능에 맡기기**
   - 장점: 스크립트 유지 비용이 없다.
   - 단점: 설치된 Orca(1.4.218)에는 코디네이터 세션 교대 기능이 없다(`run-use`는 새 터미널을 기존 Run에 붙일 뿐, 새 세션을 띄우고 한 줄을 보내는 일은 하지 않는다).

## 결과와 제한

- 무인 진행에서 사람은 digest를 나중에 읽는다. 뒤집으면 그 사이에 진행된 Story를 고쳐야 할 수 있다 — digest의 「뒤집으면」 칸이 그 비용을 적는다.
- 인계 스크립트는 Claude Code 화면 문구(입력 줄 `❯`, 상태줄의 권한 모드)에 기대어 준비를 판정한다. 화면이 바뀌면 판정이 실패하고, 그때는 인계문을 보내지 않고 멈춘다(안전한 실패). 2026-10-02 시험에서 Claude Code 2.1.287의 기본 권한 모드가 auto mode로 바뀐 것을 발견해 상태줄 공통 표시(`⏵⏵`)도 보게 했다.
- 사용량 값은 계정 전체 값이다. 한 PC에서 여러 Claude 계정을 번갈아 쓰면 마지막으로 statusline을 그린 세션의 계정 값이 남는다. Gemini는 읽을 곳이 없어 가드가 없다.
- 스크립트는 Node 20 이상이 필요하다(선택 기능에만).

## 근거

- 같은 구성(Orca + Claude Code + Codex + Gemini)으로 여러 Epic을 무인으로 운영한 기록(내부 저장소, 2026-09-11~10-01): 분할 빈도, 세션 길이와 비용, 사용량 가드 운용(하루 몫 올림), 인계 실패 사례(빈 화면에서 `tui-idle` 만족, 후임이 사람과의 대화 탭을 앞 세션으로 닫은 일, 미전송 탭 고아)와 그 대책
- [Claude Code statusline](https://code.claude.com/docs/en/statusline): Pro/Max 구독에서 `rate_limits.seven_day.used_percentage`
- 설치된 Orca 1.4.218의 `terminal create|read|send|close`, `orchestration run-use --id` 도움말
