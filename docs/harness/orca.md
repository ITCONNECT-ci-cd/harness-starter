# Orca로 개발 맡기기

이 하네스는 Epic 개발을 Orca 코디네이터에게 맡깁니다. 이 문서는 사람이 읽는 준비·운영 안내입니다. 에이전트가 따르는 규칙은 [Orca 개발 규칙](../agents/orca-rules.md)과 `AGENTS.md`의 「Orca 워커 규칙」에 있습니다.

## 어떻게 돌아가나

코디네이터(총괄 AI)는 일을 나눠 주고 결과를 확인하며, 실제 구현은 Story마다 따로 띄운 워커가 합니다.

1. 코디네이터가 Epic 계획(`plans/epic-<N>-orca.md`)을 만들고 `epic/<N>` 브랜치를 준비합니다.
2. 코디네이터가 Story별 **모델 배정안**을 표로 보여 줍니다. 사람이 OK하거나 고치기 전에는 워커를 띄우지 않습니다. 무인 진행을 골랐으면 규칙대로 적용하고 `owner-digest.md`에 남깁니다.
3. **구현 워커**가 자기 작업 폴더(워크트리)에서 story 파일 생성, TDD 구현, 빠른 검증(validate-quick), 커밋을 합니다.
4. **리뷰 워커**가 코드를 읽기만 하며 리뷰합니다. 작성자와 다른 회사의 모델이 맡아서 같은 실수를 같은 방식으로 놓칠 가능성을 줄입니다.
5. 지적 사항이 있으면 같은 구현 워커가 고칩니다.
6. 코디네이터가 Story를 `epic/<N>`에 합치고, 검증 로그·리뷰 결과·실행 기록을 `reviews/epic-<N>/`에 남깁니다.
7. 모든 Story가 끝나면 전체 검증(validate + smoke)을 돌리고 결과를 보고합니다. `develop` 병합은 따로 요청할 때만 합니다.

## 준비물 (처음 한 번)

| 항목 | 확인 방법 | 왜 필요한가 |
|---|---|---|
| Orca 설치 | `orca status --json`이 동작 | 워커 기동·메시지·정산 |
| 모델 4개 접근 | Claude Code(Sonnet 5.5, Opus 5.5), Codex(GPT-6.1 Sol, 모델 목록에 `gpt-6.1-sol`이 보이는 버전), Antigravity(Gemini 3.8 Flash) 로그인 | 역할별 배정은 [모델 배정 규칙](../agents/model-routing-rules.md) |
| 워크트리 준비 명령 | 루트 `orca.yaml`의 `scripts.setup`이 프로젝트의 의존성 설치 명령 (`templates/orca.yaml` 참고) | 새 워크트리에는 설치된 패키지가 없어 검증이 바로 실패함 |
| git hook | `./scripts/setup/install-git-hooks.sh` (Windows는 `.ps1`) | Claude가 아닌 워커의 커밋에도 걸리는 유일한 검사 |
| CI 자동 실행 (권장) | [CI/CD 기준](ci-cd.md) | 위험 명령 차단 hook은 Claude 세션에만 있음 |

`orca.yaml`이 없으면 코디네이터가 시작 확인에서 템플릿으로 만들어 커밋합니다. 스택이 npm이 아니면 준비 명령을 직접 확인하세요.

## 모델은 어떻게 고르나

코디네이터가 Story마다 두 가지를 판정해 표에서 모델과 effort를 고릅니다. 자세한 표는 [모델 배정 규칙](../agents/model-routing-rules.md)에 있습니다.

- **위험도**: 인증·권한·결제·개인정보·DB 마이그레이션·트랜잭션·동시성을 건드리면 높음, 일반 기능은 보통, 문서·설정·테스트처럼 되돌리기 쉬우면 낮음
- **작업 형태**: 기존 패턴을 따르는 정형 작업, 일반 기능, 여러 파일을 잇는 연계 작업, 설계 판단이 필요한 작업

대략 이렇게 배정됩니다. 정형 작업은 Gemini 3.8 Flash, 일반 기능은 Sonnet 5.5, 연계 작업은 GPT-6.1 Sol, 설계 판단은 Opus 5.5가 맡습니다. 위험도가 높으면 Opus 5.5나 GPT-6.1 Sol이 작성하고 다른 회사 모델이 리뷰합니다. 리뷰는 항상 작성자와 다른 회사의 모델이 하고, Flash는 리뷰하지 않습니다.

추론 수준(effort)은 위험도로 정합니다. 낮음은 medium, 보통은 high, 높음은 xhigh입니다. 다만 Sonnet 5.5와 GPT-6.1 Sol은 어떤 일이든 high 이상, 리뷰(검증)는 모델과 상관없이 high 이상, Opus 5.5의 설계 판단도 high 이상입니다. 모델이 스스로 수준을 올리지는 않으므로 배정안에 적힌 값으로 띄웁니다. high·xhigh는 medium보다 토큰과 시간이 더 들므로, 시험 운영 기록으로 효과를 확인합니다.

배정안에는 모델을 못 쓰게 됐을 때 바꿔 쓸 **대체 모델**도 함께 적습니다. 승인 뒤에는 대체 모델로의 전환과 리뷰 강화만 코디네이터가 알아서 하고, 그 밖의 변경은 다시 묻습니다.

## 코디네이터는 어떤 모델로 여나

기본은 **Sonnet 5.5 / high**(Claude Code), 위험 높음 Story가 Epic의 절반 이상이면 Opus 5.5 / medium입니다. 이유와 주의점은 README의 「코디네이터(오케스트레이터) 모델」 절에 있습니다.

## 비용과 시간 원칙

- **코디네이터는 조정만 합니다.** 구현은 워커가 하고, 한 파일 안의 작은 수정만 코디네이터가 직접 합니다. 한 줄 수정에 새 워커를 띄우면 규칙과 코드를 처음부터 다시 읽느라 오히려 비용이 듭니다.
- **사용량과 한도는 기본적으로 계산하지 않습니다.** 대신 배정안(사람 승인 또는 무인 적용 뒤 확인)으로 비싼 모델이 필요한 곳에만 쓰이게 합니다. 한도 오류가 나면 승인된 대체 모델로 넘깁니다. 하루 쓸 양을 나눠 쓰고 싶으면 아래 「사용량 한도 (선택)」를 켭니다.
- **헛걸음을 줄입니다.** 코디네이터는 워커를 기다릴 때 최대 9분씩 대기하고, 환경 확인 결과를 `state/orca/env.json`에 저장해 재사용하며, 수정 작업은 같은 워커에게 이어서 맡깁니다.
- **예산 기본값**: Story당 세션 6개(구현 1, 리뷰 1, 리뷰 내부 3, 예비 1), 90분, 같은 원인 재시도는 워커 안 3회와 대체 모델 재배정 1회입니다. 시작 프롬프트에서 바꿀 수 있습니다.

## 자리를 비우고 맡기기 (무인 진행)

시작 프롬프트의 「진행 방식」을 **무인**으로 적으면, 코디네이터가 질문으로 멈추지 않습니다. 배정안도 OK를 기다리지 않고 규칙대로 적용합니다. 대신 사람 대신 정한 것을 `reviews/epic-<번호>/owner-digest.md`에 한 줄씩 남깁니다. 돌아와서 이 파일을 읽고, 뒤집고 싶은 항목만 「이어서 하기」로 알려 주면 됩니다.

- 바뀌지 않는 것: 다른 회사 모델의 리뷰, 검증, 수락 기준, push·merge·배포 승인 범위. 무인이어도 시작 프롬프트에서 허용하지 않은 push는 하지 않습니다.
- 권한 확인 창: 아무도 없는데 Claude Code가 「이 명령을 실행해도 될까요?」를 물으면 거기서 멈춥니다. Claude Code 설정의 허용 목록에 코디네이터가 쓰는 명령(git, orca, node 스크립트, 검증 스크립트)을 넣어 두는 것을 권합니다. 권한 확인을 아예 생략하는 방법(`--skip-permissions`)도 있지만, 그때는 위험 명령 차단 hook만 남고 push 승인 범위는 규칙으로만 지켜집니다.
- 정해 둘 수 없는 결정(제품 의도, 되돌리기 비싼 설계)은 안전한 기본값으로 진행하거나 그 Story만 보류하고 다른 Story를 계속합니다. 남은 Story가 모두 막히면 멈춥니다.
- 규칙: [Orca 개발 규칙](../agents/orca-rules.md) §4.2.

## 코디네이터 세션 인계

코디네이터는 매 턴 그동안의 대화를 다시 읽으므로, 한 세션으로 Epic 전체를 돌면 뒤로 갈수록 비싸지고 앞 판단을 잘못 기억합니다. 그래서 Story 3개(계획의 「인계 주기」)마다 코디네이터가 인계문을 쓰고, 같은 모델의 새 코디네이터를 Orca 탭으로 띄워 넘깁니다. 새 코디네이터는 같은 Orca Run에 붙어 이어 갑니다. 앞 탭은 새 코디네이터가 닫습니다.

- 사람이 할 일은 없습니다. 인계가 멈추면(체인 상한, 멈춤 파일, 사용량 한도) 마지막 탭에 이유와 재개 방법이 남습니다.
- Orca 밖에서 돌리거나 인계가 실패하면, 남은 인계문 경로를 「이어서 하기」 프롬프트에 붙여 직접 엽니다.
- 규칙: [Orca 개발 규칙](../agents/orca-rules.md) §11. 스크립트: `scripts/orca/session-rollover.mjs`(Node 20 이상).

## 사용량 한도 (선택)

기본은 꺼져 있습니다. 주간 한도를 며칠에 나눠 쓰거나, 바닥나기 전에 멈추고 싶을 때 켭니다. 한도는 계정 단위라 사용자 폴더(`~/.orchestrator/`)에 둡니다.

1. `templates/orchestrator-limits.json`을 `~/.orchestrator/limits.json`으로 복사하고 숫자를 고칩니다. 예를 들어 Claude 80이면 주간 사용률 80%에서 새 작업을 멈추고, Codex 70이면 70%부터 GPT-6.1 Sol이 맡을 구현을 대체 모델로 돌립니다. 키를 빼면 그 가드만 꺼집니다.
2. Claude 사용률을 읽으려면 한 번 `node scripts/orca/install-statusline-tee.mjs`를 실행합니다. Claude Code 화면 아래 statusline이 받는 사용률을 파일로 남기는 장치이고, 원래 statusline은 그대로 보입니다. 되돌리기는 `--uninstall`입니다.
3. 하루 페이스로 쓰려면 매일 숫자를 올립니다. 올린 뒤 「이어서 하기」로 재개합니다.

언제든 멈추려면 `~/.orchestrator/STOP` 파일을 만듭니다(한 저장소만이면 `STOP-<저장소 이름>`). 코디네이터는 지금 Story의 통합까지 끝내고 멈춥니다. 한도 파일 없이도 동작합니다.

같은 계정을 다른 PC에서도 쓰면 그 사용분도 같은 사용률에 들어갑니다.

## 처음 쓸 때

사람이 기록을 직접 분석할 필요는 없습니다. 사람이 하는 일은 두 가지입니다.

1. 첫 Epic의 시작 프롬프트에서 진행 범위를 "처음 2~3개 Story"로 적습니다.
2. 코디네이터가 멈추며 보고한 조정 제안을 보고 OK하거나 고칩니다. 그다음 「이어서 하기」 프롬프트로 나머지를 진행합니다.

나머지는 AI가 합니다.
- 코디네이터가 Story마다 `reviews/epic-<N>/orca-runs.md`에 모델, 리뷰 반려 횟수, 수정 횟수, 대체 모델 전환, 소요 시간을 남깁니다.
- 멈출 때와 Epic을 끝낼 때 표의 칸별 요약과 조정 제안을 보고에 붙입니다. 예를 들어 Flash가 맡은 칸에서 반려가 절반 이상이면 그 칸을 Sonnet 5.5로 올리자고 제안합니다. 기준은 [모델 배정 규칙](../agents/model-routing-rules.md)의 「기록과 조정 제안」에 있습니다.
- 승인한 제안은 진행 중인 Epic의 남은 Story에 바로 반영됩니다. 규칙 문서의 표 자체는 Phase C 회고에서 고칩니다.

## 알려진 한계

- 사용량 가드를 켜지 않으면 사용량과 한도는 계산하지 않습니다. 한도 오류가 나면 승인된 대체 모델로 넘기고, 대체 모델도 막히면 그 Story를 보류합니다. 가드를 켜도 Gemini 사용량은 읽을 곳이 없습니다.
- 코디네이터 인계는 Orca 안에서만 자동입니다. 인계 스크립트는 화면을 읽어 후임이 준비됐는지 판정하므로, Claude Code의 화면 문구가 바뀌면 준비 판정이 실패할 수 있습니다(실패하면 인계문을 보내지 않고 멈춥니다). 그때는 「이어서 하기」로 직접 엽니다.
- 모델 이름은 논리 이름입니다. 실제 등록 ID는 코디네이터가 실행할 때 확인해 `state/orca/env.json`에 적습니다.
- `.claude/hooks`의 위험 명령 차단과 편집 시 lint는 Claude Code 세션에만 적용됩니다. Codex·Gemini 워커는 validate, git hook, CI로 확인합니다.
- Gemini 워커가 `GEMINI.md`를 통해 `AGENTS.md`를 실제로 읽는지는 처음 쓸 때 확인하세요.
- Orca 명령의 세부 값(`--worktree`, `--setup` 등)은 설치된 Orca 버전의 가이드(`orca skills get orchestration`)가 기준입니다.
